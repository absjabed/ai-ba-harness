AI BA Harness

A working method for business analysts in Claude Code. It keeps one knowledge base per project, turns meetings, documents and Jira activity into proposed changes you accept item by item, writes requirement documents from what is known, and creates Jira issues only after you have seen and approved them.

What it is

AI BA Harness is a development-workflow layer for business analysts. It runs inside Claude Code and adds nine commands, a knowledge base stored as plain markdown files, and fixed steps for anything that changes that knowledge or touches Jira. It works at project level: each project has one BA repository, which the BAs maintain and everyone else can clone and ask questions of.

9 commands

/setup, /kb-seed, /intake, /sync, /requirements, /review, /backlog, /ask and /improve-harness.

One knowledge base

Capabilities, business rules, decisions, open questions, glossary and stakeholders in knowledge/. Every statement carries its source and a status.

You accept every change

Commands write proposals to knowledge/_staging/. Pages change only after you accept each item.

Jira writes after approval

Only /backlog writes to Jira: after a duplicate check, a preview of the batch, your yes, and Claude Code's own prompt on each write.

Why use it

Most of a BA's time goes into collecting, checking and passing on what the project knows. Each row pairs a common problem with the part of the harness that handles it.

Without itWhat the harness does

What it costs, and what it doesn't do

  • Your time to accept proposals. Every staged item needs your accept, edit or reject. The first /kb-seed review is the longest; after that, daily batches are small.
  • Some git. The commands commit and ask before pushing, but someone on the BA team should be able to resolve the occasional conflict.
  • Atlassian Cloud only, through the Atlassian Rovo MCP server. Calls count against your site's rate limits and draw on Rovo credits.
  • Version 1 has no Confluence publishing and no connection to meeting-transcript tools: paste notes or drop exported transcripts in inbox/. Word, Excel and PowerPoint files need markitdown, or save them as PDF.
  • The knowledge base is only as good as what you accept. The model's extraction and judgement can miss things. A critic pass checks every staging file before you see it, but it is the same kind of model, so everything AI-drafted stays visible as a proposal until you decide.
  • Scale. Every question starts from knowledge/index.md. Once it no longer fits in one read (roughly 300 or more pages), a local search server will be needed.
  • This is version 0.5.1. Every command has been run on demo projects, twice, and the problems found were fixed, but it hasn't yet run against a real Jira site or on a live project.

Set up a project

Done once per project by the lead BA. Plan an hour for steps 1 to 5, plus the time the first /kb-seed review takes. SETUP.md in the template has the same steps.

  1. Create the repository from the template

    From a clone of ai-ba-harness, in Git Bash or a terminal:

    scripts/new-project.sh ../<project>-ba-knowledge --name "<Project name>"

    It copies everything under project/ (dotfiles included), adds HARNESS_VERSION, and records the harness version and commit in PROJECT-PROFILE.md. With --name it also fills the project name, the repository name and the README title. It never overwrites: if any file already exists in the target, it lists them and copies nothing. If the template has uncommitted changes under project/ or in HARNESS_VERSION, it stops; commit them first, or pass --allow-dirty to record the commit as <commit>-dirty. Research, design notes and examples stay behind.

  2. Put it under git and push it

    cd ../<project>-ba-knowledge
git init -b main
git add -A
git commit -m "Start from AI BA Harness 0.5.1"
git remote add origin <repository URL>
git push -u origin main

    Create the empty private repository <project>-ba-knowledge first, wherever your team keeps repositories. The automatic sync does nothing until the branch has an upstream.

  3. Connect Atlassian

    Open Claude Code in the repository folder (claude). The first time, it asks whether you trust the folder (yes: the project's settings and sync hook need it) and whether to use the atlassian server from .mcp.json (yes). Then run /mcp, choose atlassian, and sign in in the browser window that opens. It uses your own Atlassian account and permissions.

  4. Run /setup

    It interviews you in short rounds and fills PROJECT-PROFILE.md. Have these ready:

    • the Jira project key or keys, its issue types, and how you tell your team's issues apart (it proposes a scope JQL and shows how many issues it matches);
    • whether Confluence is used, which spaces, and the page published knowledge should go under later;
    • the four to eight business areas the product divides into;
    • the main stakeholders by role, what each one can decide, and who signs off recurring decisions (a short RACI);
    • the existing material /kb-seed should read;
    • the project's preferred words, and the words to avoid.

    It reads Jira's required fields for each issue type and asks how each should be filled. It shows the profile as a diff, writes it after your yes, drafts knowledge/stakeholders.md, creates a knowledge/domains/<area>/ folder per area, commits, and asks before pushing. If Atlassian isn't reachable, it finishes the local part and lists what is missing.

  5. Drop existing documents in inbox/

    The charter, specifications, process documents, glossaries. inbox/ is gitignored, so nothing in it is ever committed. Give the BAs write access to the repository now, and everyone else read access. If little is written down yet, skip the next step: hold a discovery workshop and /intake its notes instead.

  6. Run /kb-seed

    It lists what it will read (files, Confluence pages, Jira epics, with counts) and asks once. Then it writes one staging file per source to knowledge/_staging/. If more than 200 items would be staged in one run, it stops after planning and asks you to split the work, for example one area at a time. If it read Jira or Confluence, it records where it stopped, so the first /sync carries on from there.

  7. Work through the staging files

    Accept, edit or reject every item (see Staging and accepting). Accepted items become pages, each file's changes are committed, and the command asks before pushing. You can accept a whole file as draft and confirm the pages later.

  8. Bring the team in

    Send the repository URL to developers, testers and product owners: clone it once, open Claude Code in it, run /ask <question>. They answer the same two first-open prompts (the atlassian server is optional for them). Their copy updates itself whenever they open it. See For teammates.

/intake inbox/2026-09-16-discovery-workshop-notes.md

It reads

  • your typed notes from the half-day workshop
  • the knowledge base (empty so far) and stakeholders.md

It asks you

  • to accept, edit or reject each item
  • before pushing, and before deleting the raw notes

You get

Every command that changes knowledge runs the same five steps:

  1. Extract and judge. Every requirement, rule, decision, question, term and risk in the notes, each with its quote. The Product owner's "the clock starts when the driver reports it" is a decision by someone who can decide. The supervisor and the transport manager gave different accounts of who triages, so that becomes a question (Q-001), not a fact.
  2. Stage. One file in knowledge/_staging/, with the exact change for each item.
  3. Critic. A second look in a fresh context: anything left out, quotes that don't match, authority not checked, names to redact. Its findings go at the top of the file.
  4. You decide. "accept 1-24, edit 9: it's the transport manager, not the supervisor, reject 25: that was about another customer".
  5. Apply. Real IDs, pages from templates, the source record, the index and registers rebuilt, a log line, one commit, kb: intake SRC-001 discovery workshop. Then "Push?" and "Delete the raw notes from inbox/?" (default: keep).

What not to do

  • Don't edit the generated files (index.md and the registers) by hand. /review kb rebuilds them, and a hand edit is lost.
  • Don't paste raw notes straight into knowledge pages. Use /intake, so sources and conflicts are checked. Fixing a typo or wording by hand is fine as long as the meaning stays the same; add a log.md line with the command EDIT.
  • Don't create Jira issues by hand for work that has a requirement document. Use /backlog, so the duplicate check and traceability happen.
  • Don't commit anything in inbox/. It is gitignored for a reason.

The ten rules for changing it

  1. Propose, then write. Commands write proposals to _staging/ only; pages change only after you accept an item.
  2. Cite the source. Every item carries a quote and its location: file and paragraph, transcript time, Jira key and comment, Confluence page and section.
  3. Search before adding. An existing item gets an update or a link, never a duplicate.
  4. Contradictions become questions. A statement that conflicts with a confirmed or approved item becomes a Q- (or a DEC- waiting for a named approver). Nothing is overwritten.
  5. Authority decides decisions. A statement becomes a DEC- only if stakeholders.md says the speaker can decide that matter.
  6. No personal data. Roles, not names, unless a name is needed (an approver, an owner).
  7. Business language. No code paths, class names or table names in pages; technical pointers go in the source record.
  8. Log and index every change. Each accepted change appends a line to log.md and regenerates index.md and the registers.
  9. Never delete. Retire an item by setting it to superseded, with superseded_by.
  10. Raw input stays out of git. Only the redacted source record is committed.

Before you see the file, a critic reads the source again and checks the staging file against it and against the knowledge base: items left out, quotes that don't match, new items that already exist, contradictions of confirmed text, authority not checked, and data that should have been redacted. In Claude Code it runs as a sub-agent with a fresh context, so it doesn't share the first pass's blind spots. It writes nothing itself. The command fixes what the critic proved wrong, marks items it added as "added by the critic", and lists everything else in the file's Critic section for you. Start there.

For meetings, the top of the file also lists the attendees by role, the decisions (and whether the speaker could make them) and the actions, and the file ends with a play-back message for the participants.

Decide each item by ticking one of the three boxes under it (accept, edit, reject), or answer in the chat, for example:

accept 1-6, reject 7: wrong meeting, edit 8: it's 10 days not 14

Chat decisions are written into the file before anything is applied. Accepting an item accepts it as written; where the critic left a point to check, you're asked whether to take its suggestion. To finish another day or on another machine, the command commits the staging file; resuming it checks what changed in the knowledge base since.

The command applies the decided items when you say so, normally once every item is decided (say "apply the decided ones" to go earlier). It pulls again, gives the real IDs, writes the accepted items (as confirmed, or draft if you say "keep as draft"), writes the source record with the rejected items and their reasons (so they aren't proposed again), rebuilds the index and registers, appends to log.md, deletes the staging file, commits, and asks whether to push. If any accepted change affects delivery, the report ends with the affected stories and the next step: /requirements to update the document, then /review and /backlog, which updates the stories in Jira. Items you leave undecided stay in the staging file for later, and only a BA who maintains the repository applies; a teammate's run stops at the staging file. An input with more than 40 items is split into several staging files so you can decide them in sittings.

Generated files

index.md, business-rules.md, decisions.md and open-questions.md are rebuilt from the pages' properties by python tools/kb.py rebuild, which the commands run after every change (without Python, they write them by hand to the same format). Never edit them by hand. If git reports a conflict in one of them, take either side and rebuild. python tools/kb.py check checks the whole knowledge base (links, properties, IDs, rules, overdue questions and actions, and whether the generated files are current), and a GitHub workflow runs it on every push and pull request. log.md is appended, one line per accepted change:

- 2026-10-14 | INTAKE | SRC-031 | +CAP-012 ~CAP-007 +Q-014 +DEC-007 | accepted by Lead BA

In the changes column, + is new, ~ edited, x superseded and ? a question closed.

Automatic sync, in plain words

Everyone clones the BA repository once. After that, their copy updates itself. When anyone starts or resumes a Claude Code session in the repository, a small script (.claude/hooks/kb-sync.sh) runs first:

  1. It asks the shared copy whether anything new has arrived. If the network is slow or offline, it gives up after about 15 seconds and says it is working with your local copy.
  2. If there is something new and you have no unsaved edits of your own, it brings your copy up to date and prints Knowledge base updated: N new change(s) pulled from the shared copy.
  3. If you have uncommitted edits, or your copy and the shared copy have both changed, it changes nothing and tells you what to run (git pull --ff-only, or git pull --rebase and then push).

It only ever moves your copy forward, never overwrites your work, and never stops a session from starting. It does nothing in a repository that has no shared remote yet. To switch it off, set kb_auto_sync: off in PROJECT-PROFILE.md section 5.

When a BA writes, the commands pull first (so proposals are made against the latest copy), commit after you accept, and ask before pushing, because a push shares the change with everyone.

People who read in Obsidian without opening Claude Code can stay current with the Obsidian Git community plugin (set an auto-pull interval, for example 30 minutes) or a daily scheduled task, for example in Windows Task Scheduler:

git -C "<path to repository>" pull --ff-only

Open Knowledge Format

Pages are plain markdown with a type property, standard links and ISO dates, which keeps the knowledge base compatible with Open Knowledge Format. Its tool, okn, is not part of version 1 (Windows support is unconfirmed and it changes often). It may be added later if teammates need to query the knowledge base from other tools, the team wants a published site without Confluence, or the knowledge base grows to a few hundred pages and needs automatic link checks. No migration would be needed.

Definition of ready

Checked by /review and shown in the /backlog preview. A story is ready when it:

  • has the user story form and at least two acceptance criteria, including a failure or permission path where one exists;
  • relies only on business rules that exist in the knowledge base;
  • has open questions set to "None", or each marked non-blocking by the BA;
  • fits INVEST: independent, negotiable, valuable, estimable, small, testable;
  • has a fix version and a parent epic.

/backlog never creates a story with a blocking open question.

Duplicate check

Before the preview, /backlog searches the profile's Jira projects for each issue's key summary terms and area label. For each possible match it shows the existing issue and offers three choices:

ChoiceResult
linkCreate the new issue and link it to the existing one as "relates"
updateCreate nothing; propose an edit to the existing issue, shown as a diff
create anywayCreate it as planned

Approval, and the double prompt

preview table→accept / edit / decline per item→yes for the batch (≤ 15)→Claude Code prompt per write→read back→keys written back

The preview shows, per item: type, summary, parent, fix version, required fields and the duplicate verdict. More than 15 items are split into batches, with the epic in the first. After your yes for the batch, Claude Code asks again before each Jira write, because every Atlassian write tool is on the "ask" list in .claude/settings.json. That second prompt is expected: it is the last check before anything reaches Jira.

The epic is created first, then each story with the epic as parent, one at a time. Each created issue is read back to confirm the summary, type, parent, fix version and required fields stuck; if one didn't, the report says so and offers a fix. If a create fails, the batch stops and the report lists what was and wasn't created. /backlog never deletes or transitions existing issues.

For teammates

Developers, testers, product owners and new BAs can ask the project's knowledge questions without learning any of the BA commands.

  1. Clone once

    git clone <repository URL>

    You need read access to the repository, Claude Code, and Git (with Git Bash on Windows, for the automatic sync). Atlassian sign-in is optional: without it, /ask answers from the knowledge base only.

  2. Open Claude Code in the folder and ask

    claude
/ask who can raise a job card?

    Your copy updates itself whenever you open Claude Code there.

Reading an answer

  • Every claim is followed by the page and ID it comes from, for example (CAP-012, BR-104), linked to the page.
  • Confirmed and approved content is stated plainly. Draft content carries "(unconfirmed: draft page)". Superseded content is never used.
  • Results from Jira or Confluence are labelled as such, and are not treated as confirmed knowledge.
  • When something touches an open question, the answer says so and links the Q-.
  • Before answering, /ask checks each claim against the page it cites. If it had to drop a claim, it tells you the knowledge base doesn't confirm that part.
  • When the knowledge base doesn't know, the answer says "The knowledge base doesn't answer this." and drafts an open question for you to send to the BA: the question, why you need it, and who might know.

/ask is read-only by design: it has no write, edit, shell or sub-agent tools, and every Jira and Confluence write tool is disallowed for it. Other assistants (Copilot, Cursor, Codex) follow AGENTS.md in the repository and answer the same way. You can also read the pages directly: start at knowledge/index.md, on GitHub or in Obsidian.

Suggesting a change

Send the material to the BA. Or run /intake on it: it asks whether you maintain the repository, and for anyone else it stops once the proposal is written, tells you in plain words what was proposed, and offers to put it on a branch (kb/stage-<slug>) for a pull request that only adds the staging file. Keep your original note until the BA has dealt with it. Either way, the BA accepts or rejects each item, and nothing changes until then.
