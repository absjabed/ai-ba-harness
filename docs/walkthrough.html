A month on FleetKeep

One project, from an empty template to a working knowledge base, a reviewed requirement and stories in Jira. Every command appears at the moment a BA would reach for it, with what it reads, what it asks you and what you end up with.

Hypothetical, but checkable. FleetKeep, Northwind Systems and everyone in it are fictional. The end state of this story is real files: the worked example in the template at examples/fleetkeep-ba-knowledge/. Wherever this page says "you get", the file it names is there to open. The chat exchanges are illustrations of what the commands ask; the exact wording varies from run to run.

The project and the cast

Day 0: before /setup

About fifteen minutes of plumbing. /setup can't run until the repository exists and Claude Code is open in it.

  1. Create the repository from the template

    scripts/new-project.sh ../fleetkeep-ba-knowledge --name "FleetKeep"

    Copies the harness into ../fleetkeep-ba-knowledge, and fills the project name, the repository name fleetkeep-ba-knowledge, the README title and the harness version and commit. Nothing else is filled yet.

  2. Put it under git and push it

    cd ../fleetkeep-ba-knowledge
git init -b main
git add -A
git commit -m "Start from AI BA Harness 0.3.0"
git remote add origin <URL of the empty private repository>
git push -u origin main

  3. Open Claude Code and answer two prompts

    Run claude in the folder. The first time, Claude Code asks whether you trust the folder (yes, or the sync hook and the project's permission rules won't run) and whether to use the atlassian server from .mcp.json (yes).

  4. Sign in to Atlassian

    /mcp, choose atlassian, sign in in the browser with your own account. No token is stored anywhere in the repository.

Day 0: /setup, round by round

Based on

  • your answers in the interview
  • what Jira and Confluence report: projects, issue types, versions, link types, required fields, spaces
  • the template's PROJECT-PROFILE.md and conventions

It asks you

  • eight short rounds, three to five questions each, with a proposed answer where it can make one
  • how to fill each required Jira field
  • a yes before writing, and before pushing

You get

  • a filled PROJECT-PROFILE.md
  • knowledge/stakeholders.md with a RACI (draft)
  • one folder per business area, a log line, one commit

It never writes to Jira or Confluence, never stores a password, and never invents a stakeholder, a field rule or a JQL you didn't confirm. Plan 30 to 45 minutes.

Had the sign-in failed, it would tell you to run /mcp and carry on with the parts that don't need Jira. Had the profile been filled already, it would show what's there and ask which sections to change, never overwriting one without a yes.

After /setup: what you do next

The repository is configured but the knowledge base is still empty. /ask would answer "the knowledge base doesn't answer this" to everything, so don't invite the team yet.

  1. Set repository access

    BAs who maintain it: write. Developers, testers, product owners: read. Teammates who want to suggest a change open a pull request with a staging file; only a BA applies it.

  2. Choose how the first knowledge arrives

    Material existsCharter, specs, process documents, a Confluence tree, open epics: drop the files in inbox/ and run /kb-seed. One staging file per source; if it read Jira or Confluence, it records where it stopped so the first /sync carries on from there
    Little is written downHold a discovery workshop, save the notes in inbox/ and run /intake. FleetKeep took this path

  3. Work through the first staging files

    The longest review you'll do. Read each file's Critic section first, then accept, edit or reject each item. Accepted items become pages and are committed; you're asked before each push.

  4. Invite the team

    Once the main areas have pages, send the repository URL: "Clone it, open Claude Code in it, ask /ask <question>." Their copies update themselves.

  5. Put the rhythm in your calendar

    /sync each morning, /intake after each meeting or document, /review kb on Fridays.

Sep 17: the first knowledge, from a workshop

/intake inbox/2026-09-16-discovery-workshop-notes.md

Based on

  • your typed notes from the half-day workshop
  • the knowledge base (still empty) and stakeholders.md

It asks you

  • to decide each staged item
  • whether to redact a name or two
  • before pushing, and before deleting the raw notes

You get

  • the first glossary, four capabilities, three entities, a process with its diagram, a decision, two questions
  • SRC-001, the redacted source record
  1. Extract and judge. Every requirement, rule, decision, question, term and risk in the notes, each with its quote. The Product owner's "the clock starts when the driver reports it" is a decision by someone who can decide; the two contradicting accounts of who triages become a question (Q-001).
  2. Stage. One file in knowledge/_staging/, with the exact change for each item.
  3. Critic. A second look, in a fresh context: it re-reads the notes for anything left out, checks every quote, re-searches the knowledge base, and checks authority and redaction. Its findings go into the file's Critic section.
  4. You decide. "accept 1-24, edit 9: it's the transport manager, not the supervisor, reject 25: that was about another customer".
  5. Apply. Real IDs, pages from templates, the source record, regenerated index and registers, a log line, one commit: kb: intake SRC-001 discovery workshop. Then "push?" and "delete the raw notes from inbox/?" (default: keep).

Oct 6: what happened in Jira

/sync jira

Based on

  • FK issues in the scope JQL updated since the last sync, with their comments and change history
  • the existing source records, so nothing is proposed twice

It asks you

  • on the first run only: how far back to go (you say "since Sep 28")
  • to decide each staged item

You get

  • Q-001 answered from a Jira comment
  • CAP-003 superseded by CAP-004, because FK-1188 shows category B escalates too
  • DEC-002 (confirmed) and DEC-003 (approved)

It reads Jira and never writes to it, not even a comment. It ignores routine status moves, estimates and assignee changes on eleven other issues. Watch the authority check at work: the Engineering lead's comment recorded that the Product owner agreed something at stand-up. That is second-hand, so DEC-002 stays confirmed, not approved, until the Product owner confirms it. The sync time in knowledge/_meta/sync.json moves only after you have decided every item. Result: SRC-003.

After the first run, /sync is a daily habit: two to ten items most mornings.

Any day: a developer asks

/ask when does a category-B defect escalate, and does it count overnight?
Claude

A category-B defect is escalated to the transport manager when it has had no triage outcome 36 hours after it was reported (CAP-004, BR-016). The clock starts when the driver reports it, not at triage (BR-017, DEC-001, approved).

Whether it keeps counting overnight is still open: Q-002 is with the Product owner. (An answer is waiting in a staging file, but the BA hasn't accepted it yet, so it isn't knowledge.)

Before answering, /ask re-opened each cited page to check it says what the answer claims. It has no tools that write, run commands or start sub-agents. Asked something the knowledge base doesn't cover, it says so and drafts a question for the developer to send you.

Fridays: the health check

/review kb

Reports broken links, pages missing from the index, drafts older than 30 days, questions past their due date, staging files older than a day, contradictions between pages, and terms used differently from the glossary. On Friday Oct 16 it would flag the triage-call staging file if you hadn't decided it yet, and remind you that two areas, inspections and tenancy-and-access, have no pages at all. It rebuilds the index and registers, commits only those, and asks before pushing.
